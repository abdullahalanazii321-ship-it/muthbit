# منصة مثبت

[![CI](https://github.com/abdullahalanazii321-ship-it/muthbit/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/abdullahalanazii321-ship-it/muthbit/actions/workflows/ci.yml)

منصة مشتريات موثّقة للشركات: موردون موثّقون، وسقوف إنفاق يفرضها النظام، وسلسلة اعتماد قبل أي التزام مالي، وسجل تدقيق لا يُعدَّل.

هذا المستودع يحتوي **المرحلة الأولى**: الأساس التقني — قاعدة البيانات، المصادقة، عزل الأدوار، محرك السقوف والاعتمادات، سجل التدقيق، وطبقة هوية مثبت جاهزة للواجهة.

---

## المكدّس التقني

| الطبقة | التقنية |
|---|---|
| الخادم | Node.js + Express |
| قاعدة البيانات | PostgreSQL 16 عبر Knex |
| المصادقة | JWT + bcrypt، ومفاتيح API للوكلاء الأذكياء |
| الحماية | helmet · CORS مقيّد · تحقّق مدخلات بـ zod |
| الواجهة (المرحلة الثانية) | React + Vite + Tailwind بترتيب RTL |
| النشر | Render |

---

## التشغيل محلياً

```bash
# 1) المتطلبات: Node 20+ و PostgreSQL 16
createdb muthbit_dev

# 2) الاعتماديات
npm install

# 3) متغيرات البيئة
cp .env.example apps/api/.env
#    عدّل DATABASE_URL و JWT_SECRET

# 4) الجداول والبيانات التجريبية
npm run api:migrate
npm run api:seed

# 5) التشغيل
npm run api:dev        # http://localhost:4000

# 6) اختبار المسار الكامل
cd apps/api && npm test
```

## المبادئ التي بُني عليها الكود

**١. الافتراض هو المنع.** لا يوجد فرع `else` يسمح بالمرور عند الغموض. موظف بلا سقف مضبوط لا يشتري — غياب السقف ليس صلاحية مفتوحة. دور غير معروف يُرفض بدل أن يُعامل كضيف.

**٢. لا استعلام بلا نطاق.** `scopeToCompany` و`scopeToSupplier` في `src/middleware/auth.js` يقيّدان كل استعلام بالشركة أو المورد، و`assertOwnership` يتحقق من كل صف مقروء قبل تسليمه. مدير المنصة وحده مستثنى، وبشكل صريح.

**٣. النطاق يُقرأ من قاعدة البيانات لا من الرمز.** رمز JWT قديم لمستخدم أُوقف أو نُقلت شركته لا ينفع: كل طلب يعيد قراءة حالة المستخدم وشركته.

**٤. سجل التدقيق غير قابل للتعديل.** ليس بقاعدة في التطبيق، بل بـ trigger في PostgreSQL يرفض أي `UPDATE` أو `DELETE` على `audit_log`. حتى لو أخطأ الكود أو تسرّبت صلاحية قاعدة البيانات، السجل يبقى.

**٥. القيد داخل المعاملة.** كل حدث يُقيَّد في نفس المعاملة التي نفّذته، فلا يُسجَّل شيء لعملية فشلت ولا تنجح عملية بلا أثر.

**٦. تجاوز السقف تصعيد لا رفض.** المبلغ فوق سقف المشتري لا يوقف الطلب، بل يرفعه للمدير المالي أو المالك. أما الفئة غير المصرّح بها والسقف الشهري فحجب صلب.

**٧. لا أحد يعتمد طلبه.** يُمنع على مستوى الدور وعلى مستوى الصف معاً.

## هيكل المستودع

```
apps/api/
  knexfile.js
  src/
    config/env.js              متغيرات البيئة — الإنتاج يرفض الإقلاع بمفتاح افتراضي
    db/
      knex.js
      migrations/              المخطط الكامل
      seeds/                   البيانات التجريبية
    middleware/
      auth.js                  المصادقة، الأدوار، العزل fail-closed
      errorHandler.js          ترجمة أخطاء قاعدة البيانات لرسائل عربية
    services/
      policy.js                محرك السقوف والاعتمادات
    routes/
      auth.routes.js           تسجيل الشركات، الدخول، /me
      companies.routes.js      التوثيق، المستخدمون، السقوف، الإيقاف الفوري
      suppliers.routes.js      تسجيل الموردين وتوثيقهم
      requests.routes.js       الطلبات، اختيار العرض، الاعتماد، أمر الشراء
      offers.routes.js         جانب المورد
      audit.routes.js          قراءة السجل، مقيّدة بالنطاق
      categories.routes.js
  tests/smoke.js               ٥٠ فحصاً للمسار الكامل

packages/design/               هوية مثبت: التوكنز وإعداد Tailwind المشترك
```

## المخطط

| الجدول | الغرض |
|---|---|
| `companies` | الشركات المشترية وحالة توثيقها |
| `suppliers` | الموردون والوكلاء التجاريون وحالة توثيقهم وتقييمهم |
| `categories` · `supplier_categories` | الفئات، وما يُصرّح للمورد بالعرض فيه |
| `users` | كل الحسابات، بقيد يمنع انتماء مستخدم لشركة ومورد معاً |
| `buyer_limits` | سقف الطلب الواحد، السقف الشهري، الفئات المسموحة، المعتمِد |
| `agents` | هوية الوكيل الذكي ومفتاحه، قابلة للإلغاء لحظياً |
| `requests` | طلبات الشراء ولقطة قرار السياسة لحظة الاختيار |
| `offers` | عروض الموردين — الناقص منها محجوب عن المشتري |
| `approvals` | كل قرار اعتماد أو رفض مع سببه والمبلغ وقت القرار |
| `purchase_orders` | أوامر الشراء بشروط العرض المعتمد نفسها |
| `audit_log` | سجل الأحداث، إضافة فقط |

## الاختبار

`npm test` داخل `apps/api` يشغّل ٥٠ فحصاً على قاعدة بيانات حقيقية، تغطي:

- تسجيل الدخول ورفض الحسابات غير المفعّلة
- حجب العروض الناقصة عن المشتري مع عدّها
- عدم كشف هوية الشركة الطالبة للمورد
- العزل بين الشركتين: القراءة والقائمة والقرار
- اختيار العرض ضمن السقف، والتصعيد فوقه
- منع اعتماد المرء لطلبه، ومنع معتمِد غير موجّه له الطلب
- الرفض بلا سبب مكتوب
- إصدار أمر الشراء مرة واحدة بشروط العرض نفسها
- منع الفئة غير المصرّح بها، ومنع موظف بلا سقف
- منع المورد غير الموثّق من العرض
- الإيقاف الفوري وإلغاء الطلبات المفتوحة دون المساس بما صدر أمره
- رفض قاعدة البيانات لتعديل أو حذف سجل التدقيق

## المرحلة الثانية

الواجهة: React + Vite + Tailwind RTL مبنية على `packages/design`، بشاشات الدخول، ولوحة الشركة، وشاشة الاعتماد، وبوابة المورد، وعارض سجل التدقيق.

## المرحلة الثالثة

ربط التحقق الآلي بمنصة واثق للسجل التجاري، ومطابقة زاتكا في الفوترة، وواجهة الوكلاء الأذكياء بمفاتيح قابلة للإلغاء.

مولّد مفاتيح الوكلاء يجب أن يضمن تفرّد `api_key_prefix` — إما بقيد `unique` أو بتحقق المولّد نفسه.

رموز الدخول تحتاج refresh token أو قائمة إبطال قبل أن يقصَّر عمرها.

## ملاحظة أمنية

`JWT_SECRET` في `.env.example` قيمة تطوير. في الإنتاج يرفض الخادم الإقلاع بدون مفتاح حقيقي — راجع `src/config/env.js`. ولا تُرفع `.env` إلى المستودع.
